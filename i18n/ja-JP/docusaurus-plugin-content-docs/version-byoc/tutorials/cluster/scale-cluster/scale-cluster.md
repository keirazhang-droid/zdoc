# クラスターのスケーリング

Zilliz Cloud では、**クエリ CU** はインデックスを提供し、検索リクエストを処理するために使用されるハードウェアリソースのセットです。クエリ CU は、クエリサービスを実行する完全管理型の物理ノードと考えることができます。**レプリカ** は、同じリソースとデータを含むクラスターレベルのコピーです。クエリ CU は主にクラスターの容量とコンピューティングリソースを決定し、レプリカはクエリを提供するための追加の並列処理を提供します。

## Query CU と レプリカ\{#query-cu-vs-replica}

ワークロードが増加し、より多くのデータが書き込まれると、サービングクラスターは最終的に容量とパフォーマンスの限界に達する可能性があります。これを事前に管理するために、メトリクスページで **Query CU 容量** と **Query CU 計算** を監視し、限界に達する前に **スケーリング** を行うことができます。

クエリ CU またはレプリカのどちらをスケーリングするかの選択は、目標によって異なります。経験則としては：

- 1～8 クエリ CU のサービングクラスターの場合、クエリ CU を直接スケーリングできます。
- 8 クエリ CU を超えるサービングクラスターの場合、必要に応じてクエリ CU またはレプリカをスケーリングできます。

### 容量を増やすためのクエリ CU のスケーリング\{#scale-query-cus-for-more-capacity}

容量に関連する制限に達している場合、またはデータとワークロードの継続的な成長が見込まれる場合は、クエリ CU をスケーリングしてください。

一般的な兆候とシナリオは次のとおりです。

- 書き込み操作は失敗するが、読み取りは成功する。これは多くの場合、サービングクラスターが容量に達しているか、その近くにあることを示します。
- 大規模なデータセットを扱っている場合、またはより多くのコレクションが必要な場合。
- CPU またはメモリの使用率が高い場合。

詳細については、[クエリ CU のスケーリング](./scale-query-cu) を参照してください。

### スループットまたは可用性を高めるためのレプリカのスケーリング\{#scale-replicas-for-higher-throughput-or-availability}

サービングクラスターがデータを保持できるが、クエリスループット (QPS) のボトルネックが発生している場合、または可用性を向上させる必要がある場合は、レプリカをスケーリングしてください。

一般的な兆候とシナリオは次のとおりです。

- 小規模から中規模のデータセットだが、QPS のボトルネックが発生している。
- クエリ負荷を複数の同一コピーに分散してスループットを向上させたい。
- 可用性を向上させたい。

詳細については、[レプリカのスケーリング](./manage-replica) を参照してください。

## スケーリングオプション\{#scaling-options}

Zilliz Cloud は、サービングクラスターのリソースをスケーリングするための複数の方法を提供します。ワークロードパターンに応じて、即時、スケジュール、または自動でスケーリングできます。

### 手動スケーリング\{#manual-scaling}

ワークロードを明確に把握しており、いつ変更が必要かを予測できる場合は、手動でリソースを調整します。

- **クエリ CU:** 容量を拡張するために増やし、需要が低下したときにコストを削減するために減らします。
- **レプリカ:** クエリスループットと可用性を向上させるために増やし、需要が低下したときに減らします。

### スケジュールされたスケーリング\{#scheduled-scaling}

ワークロードに**繰り返しパターン**がある場合（例：平日のピークと週末の谷間）は、スケジュールされたスケーリングを使用します。一般的なユースケースには、営業時間中のトラフィックスパイクや予測可能なバッチ/クエリウィンドウが含まれます。

スケジュールされたスケーリングのために、Zilliz Cloud は 2 つのモードを提供します：

- **基本モード**: スケジュールを定義するためのシンプルなセレクター
- **詳細モード**: より柔軟性を高めるために [Unix cron 式](./cron-expression) を使用します。

### 動的スケーリング\{#dynamic-scaling}

**予測不可能なワークロード**に対して動的スケーリングを有効にします。Zilliz Cloud は、リアルタイムメトリクスに基づいて、ユーザー定義の**最小-最大範囲**内でリソースを自動調整します。

- **クエリ CU:** **CU 容量**メトリクス値に基づいて自動スケーリングされます。
- **レプリカ:** **CU 計算**メトリクス値に基づいて自動スケーリングされます。

## よくある質問\{#faqs}

**どのスケーリングオプションを選択すべきですか？**

以下は、ニーズに合った適切なスケーリング方法を選択するためのクイックヒントです：

![ZsKhw59w5hZv4RbjorlclAaEn4e](https://zdoc-images.s3.us-west-2.amazonaws.com/ZsKhw59w5hZv4RbjorlclAaEn4e.png)

- ワークロードパターンを非常によく理解している場合（一貫した毎日のピークや計画されたバッチインポートジョブなど）、**手動**スケーリングと**スケジュール**スケーリングが適切なオプションです。クエリ CU をすぐに調整する必要がある場合は、手動スケーリングを選択してください。特定の将来の時間に繰り返し調整を行いたい場合は、スケジュールされたスケーリングを選択してください。
- ワークロードが予測不可能で、日または週を通して変動する場合は、**動的スケーリング**が推奨されます。定義した範囲内でサービングクラスターのサイズを自動的に調整し、コストを最適化しながらパフォーマンスを維持するのに役立ちます。

**レプリカはいつスケーリングすべきで、クエリ CU はいつスケーリングすべきですか？**

次のことをお勧めします：

- **レプリカ**数を増やす場合：
    - 高 QPS（1 秒あたりのクエリ数）と高可用性を処理する必要がある場合。
    - ワークロードが多くの同時検索またはクエリ要求で構成されている場合。スループットを向上させる必要がある。
    *ヒント: 各レプリカはクエリ CU リソースの独立したコピーであり、クエリのサブセットを処理します。*
- **クエリ CU**を増やす場合：
    - 大規模なデータセットを扱っている場合、またはより多くのコレクションが必要な場合。
    - CPU またはメモリの使用率が高い場合。
    *ヒント: CU サイズを大きくすると、各クエリノードにより多くのコンピューティングリソースと容量が提供されます。*
- **提案**: 1～8 CU のサービングクラスターの場合、クエリ CU を直接スケーリングできます。8 CU を超えるサービングクラスターの場合は、レプリカを増やしてください。

**Zilliz Cloud ではスケーリングはどのように機能しますか？**

次の図は、Zilliz Cloud でのスケーリング操作のワークフローを示しています。

![ORwIwl2z2h0XxLbFNLBcdFOlneh](https://zdoc-images.s3.us-west-2.amazonaws.com/ORwIwl2z2h0XxLbFNLBcdFOlneh.png)

- **スケーリングの開始**: Web コンソールまたは RESTful API を介してスケーリングリクエストを送信できます。
- **リソースチェック**: Zilliz Cloud は、次の要件に対してスケーリングリクエストを検証します。
    - エンタープライズプロジェクト: クエリ CU × レプリカ ≤ 10,240
    - 標準プロジェクト: クエリ CU ≤ 32
    - レプリカ > 1 の場合、サービングクラスターは 12 クエリ CU 未満にスケールダウンできません。
    - 現在のデータ量 < 新しい CU サイズの CU 容量の 80%
    - 現在のコレクション数とパーティション数 < 新しい CU サイズで許可される[コレクション数とパーティション数の最大値](./limits#collections)
    - スケーリングに関して問題がある場合は、[サポートにお問い合わせください](http://support.zilliz.com)。
- **スケーリングジョブの生成**: リソースチェックが通過すると、Zilliz Cloud はスケーリングジョブを作成します。[ジョブ](./job-center) ページで進行状況を追跡できます。この間、サービングクラスターのステータスは **変更中** に変わり、サスペンド、移行、ドロップなどのクラスター操作は利用できなくなります。
- **ジョブが完了しました**: ジョブが完了すると、スケーリングは成功し、サービングクラスターのステータスは **Running** に戻ります。また、リソース調整を確認するメールが届きます。

**専用クラスターをスケーリングする場合、スケーリング中は古い構成と新しい構成のどちらに基づいて請求されますか？**

[スケーリング](./scale-cluster)中は、以前の構成に基づいて請求されます。新しい構成は、スケーリングジョブが正常に完了した後でのみ請求に使用されます。
