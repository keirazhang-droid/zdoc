# クラスターのスケーリング

Zilliz Cloud において、**クエリ CU** は、インデックスを提供し検索リクエストを処理するために使用されるハードウェアリソースのセットです。クエリ CU は、クエリサービスを実行する完全管理型の物理ノードと考えることができます。**レプリカ** は、同じリソースとデータを含むクラスターレベルのコピーです。クエリ CU は主にクラスターの容量とコンピューティングリソースを決定し、レプリカはクエリを提供するための追加の並列性を提供します。

<Admonition type="info" icon="📘" title="Note">

この記事で説明するスケーリングオプションは、**サービングクラスター** にのみ適用されます。

**オンデマンドクラスター** は自動的にスケーリングされます。リクエストが到着すると起動し、アイドル時にはゼロにスケールバックするため、手動での操作は必要ありません。

</Admonition>

## クエリ CU とレプリカの比較 \{#query-cu-vs-replica}

ワークロードが増加し、より多くのデータが書き込まれるにつれて、サービングクラスターは最終的に容量とパフォーマンスの限界に達する可能性があります。これを事前に管理するには、メトリクスページで **Query CU容量** と **Query CU計算** を監視し、限界に達する前に**スケーリング**を実行します。

クエリ CU とレプリカのどちらをスケーリングするかは、目標によって異なります。一般的な目安としては、以下のようになります。

- 1～8 クエリ CU のサービングクラスターの場合、クエリ CU を直接スケーリングできます。

- 8 クエリ CU を超えるサービングクラスターの場合は、必要に応じてクエリ CU またはレプリカをスケーリングできます。

### 容量を増やすためのクエリ CU のスケーリング \{#scale-query-cus-for-more-capacity}

容量関連の制限に達している場合、またはデータとワークロードの継続的な成長が見込まれる場合は、クエリ CU をスケーリングします。

典型的なシグナルとシナリオは次のとおりです。

- 書き込み操作は失敗するが、読み取りは成功する。これは多くの場合、サービングクラスターが容量に達しているか、容量に近づいていることを示します。

- 大規模なデータセットを扱っている、またはより多くのコレクションが必要である。

- CPU またはメモリ使用率が高い。

詳細については、[Query CU のスケーリング](./scale-query-cu) を参照してください。

### スループットまたは可用性を高めるためのレプリカのスケーリング \{#scale-replicas-for-higher-throughput-or-availability}

サービングクラスターがデータを保持できるが、クエリスループット (QPS) のボトルネックが見られる場合、または可用性を向上させる必要がある場合に、レプリカをスケーリングします。

典型的なシグナルとシナリオは次のとおりです。

- 小規模から中規模のデータセットであるが、QPS のボトルネックが発生している。

- クエリ負荷を複数の同一コピーに分散してスループットを向上させたい。

- 可用性を向上させたい。

詳細については、[レプリカのスケーリング](./manage-replica) を参照してください。

## スケーリングオプション \{#scaling-options}

Zilliz Cloud は、サービングクラスターのリソースをスケーリングするための複数の方法を提供します。ワークロードのパターンに応じて、即時、スケジュールに従って、または自動的にスケーリングできます。

### 手動スケーリング \{#manual-scaling}

ワークロードを明確に理解しており、変更が必要なタイミングを予測できる場合は、リソースを手動で調整します。

- **クエリ CU:** 需要が増加した場合は容量を増やし、需要が減少した場合はコスト削減のために減らします。

- **レプリカ:** クエリスループットと可用性を高めるために増やし、需要が減少した場合は減らします。

### スケジュールされたスケーリング \{#scheduled-scaling}

ワークロードに**繰り返しパターン**（平日のピークや週末の谷間など）がある場合は、スケジュールされたスケーリングを使用します。一般的なユースケースとしては、営業時間中のトラフィック急増や、予測可能なバッチ/クエリウィンドウなどがあります。

スケジュールされたスケーリングでは、Zilliz Cloud は 2 つのモードを提供します。

- **基本モード**: スケジュールを定義するためのシンプルなセレクター

- **詳細モード**: [Unix cron 式](./cron-expression) を使用して柔軟性を高めます。

### 動的スケーリング \{#dynamic-scaling}

**予測不可能なワークロード**に対して動的スケーリングを有効にします。Zilliz Cloud は、リアルタイムメトリクスに基づいて、ユーザーが定義した**最小-最大範囲**内でリソースを自動的に調整します。

- **クエリ CU:** **CU容量** メトリクス値に基づいて自動スケーリングされます。

- **レプリカ:** **CU計算** メトリクス値に基づいて自動スケーリングされます。

## スケーリング中の請求 \{#billing-during-scaling}

専用クラスターの場合、スケーリングによってすぐに請求が変更されるわけではありません。スケーリングジョブの実行中、Zilliz Cloud は以前の構成に基づいてクラスターの請求を継続します。新しいクエリ CU またはレプリカの構成が請求に使用されるのは、スケーリングジョブが正常に完了した後です。

詳細については、[専用クラスターのコスト](./dedicated-cluster-cost) を参照してください。

## FAQ \{#faqs}

**どのスケーリングオプションを選択すればよいですか？**

以下は、ニーズに適したスケーリング方法を選択するためのクイックヒントです。

![ZsKhw59w5hZv4RbjorlclAaEn4e](https://zdoc-images.s3.us-west-2.amazonaws.com/ZsKhw59w5hZv4RbjorlclAaEn4e.png)

- ワークロードのパターン（一貫した日次ピークや計画されたバッチインポートジョブなど）を非常によく理解している場合は、**手動**スケーリングと**スケジュールされた**スケーリングが適切な選択肢です。クエリ CU をすぐに調整する必要がある場合は、手動スケーリングを選択します。調整を特定の将来の時間に繰り返し発生させたい場合は、スケジュールされたスケーリングを選択します。

- ワークロードが予測不可能で、日時や週によって変動する場合は、**動的スケーリング**をお勧めします。サービングクラスターのサイズをユーザーが定義した範囲内で自動的に調整し、パフォーマンスを維持しながらコストを最適化します。

**いつレプリカをスケーリングし、いつクエリ CU をスケーリングすればよいですか？**

以下をお勧めします。

- **レプリカ**数を増やす場合：

    - 高い QPS (1 秒あたりのクエリ数) と高い可用性を処理する必要がある場合。

    - ワークロードが多くの同時検索またはクエリリクエストで構成されている場合。スループットを向上させる必要がある。

    *ヒント: 各レプリカはクエリ CU リソースの独立したコピーであり、クエリのサブセットを処理します。

- **クエリ CU** を増やす場合：

    - 大規模なデータセットを扱っている、またはより多くのコレクションが必要である場合。

    - CPU またはメモリ使用率が高い場合。

    *ヒント: CU サイズを増やすと、各クエリノードにより多くのコンピューティングリソースと容量が提供されます。

- **提案**: 1～8 CU のサービングクラスターの場合は、クエリ CU を直接スケーリングできます。8 CU を超えるサービングクラスターの場合は、レプリカを増やしてください。

**Zilliz Cloud ではスケーリングはどのように機能しますか？**

次の図は、Zilliz Cloud でのスケーリング操作のワークフローを示しています。

![ORwIwl2z2h0XxLbFNLBcdFOlneh](https://zdoc-images.s3.us-west-2.amazonaws.com/ORwIwl2z2h0XxLbFNLBcdFOlneh.png)

- **スケーリングの開始**: Web コンソールまたは RESTful API を介してスケーリングリクエストを送信できます。

- **リソースチェック**: Zilliz Cloud は、次の要件に対してスケーリングリクエストを検証します。

    - エンタープライズプロジェクト: クエリ CU × レプリカ ≤ 10,240

    - スタンダードプロジェクト: クエリ CU ≤ 32

    - レプリカ > 1 の場合、サービングクラスターは 12 クエリ CU 未満にスケールダウンできません。

    - 現在のデータ量が、新しい CU サイズの CU 容量の 80% 未満であること。

    - 現在のコレクション数とパーティション数が、新しい CU サイズで許可されている[コレクションとパーティションの最大数](./limits#collections)未満であること。

    - スケーリングに関して問題がある場合は、[サポートにお問い合わせください](http://support.zilliz.com)。

- **スケーリングジョブの生成**: リソースチェックに合格すると、Zilliz Cloud はスケーリングジョブを作成します。進行状況は [ジョブ](./job-center) ページで追跡できます。この間、サービングクラスターのステータスは**変更中**に変わり、一時停止、移行、削除などのクラスター操作は使用できなくなります。

- **ジョブが完了しました**: ジョブが完了すると、スケーリングは成功し、サービングクラスターのステータスは**実行中**に戻ります。また、リソース調整を確認するメールが届きます。

**専用クラスターをスケーリングする場合、スケーリング中は古い構成と新しい構成のどちらに基づいて請求されますか？**

[スケーリング](./scale-cluster)中は、以前の構成に基づいて請求されます。新しい構成が請求に使用されるのは、スケーリングジョブが正常に完了した後です。
