        ## [BYOC] マルチデータプレーンサポート\{#byoc-multi-dataplane-support}

        Zilliz Cloud BYOCは、1つのプロジェクト内で複数のデータプレーンをサポートするようになりました。BYOCプロジェクトは複数のリージョンにまたがることができ、各データプレーンはリージョン固有のインフラストラクチャユニットを表します。

        - **複数のデータプレーン** を1つのBYOCプロジェクトで管理し、**新しいデータプレーンページ** でデータプレーン管理を実行できます。

        - プロジェクト内でターゲットリージョン/データプレーンを選択してクラスターを作成できます。

        既存のBYOCプロジェクトは互換性を維持しており、データ移行は必要ありません。現在のBYOCプロジェクトは、1つのデータプレーンを持つプロジェクトとして引き続き動作します。

        詳細については、[AWSへのBYOCのデプロイ](/docs/byoc/deploy-byoc-aws)、[AWSへのBYOC-Iのデプロイ](/docs/byoc/deploy-byoc-i-aws)、[Microsoft AzureへのBYOC-Iのデプロイ](/docs/byoc/deploy-byoc-i-azure)、[GCPへのBYOCのデプロイ](/docs/byoc/deploy-byoc-gcp)をご参照ください。

        ## Vector Lakebase パブリックプレビュー\{#vector-lakebase-public-preview}

        このメジャーリリースでは、Zilliz Cloudはベクトルデータベース製品からVector Lakebaseプラットフォームへと進化します。

        アップグレード後、元のベクトルデータベースサービスはレイテンシが重要なワークロード向けのリアルタイムサービングレイヤーとなり、プラットフォームはデータとコンピューティングの全体的な機能を拡張し、最新のAIおよびエージェントアプリケーションに必要なセマンティック検索と分析ワークフローループをより適切にサポートします。

        Vector Lakebaseは、S3ベースの統一データ基盤上に構築され、3つのアクセスモードでAIおよびエージェントのワークロードを強化します。

        - **リアルタイム検索**: レイテンシが重要な本番サービング向け。
        - **反復的発見**: インタラクティブかつマルチステップの探索向け。
        - **バッチ分析**: オフラインマイニングとデータセット最適化向け。

        Vector Lakebaseは、完全に分離されたストレージ・コンピューティングアーキテクチャ上に構築されています。データはデータベース（プロジェクトレベルのベクトルストアで、どのコンピューティングクラスターからも独立）に保存され、チームはテキスト、JSON、ラベル、地理空間データ、その他のタイプの属性とともに無制限のベクトルを保存できます。

        特に、Zilliz Vector Lakebaseはいくつかの主要な機能を導入します。

        **オンデマンド検索**

        インタラクティブな発見とバッチ分析は、多くの場合、オンラインサービングよりも1～3桁大きいデータセット（フィードバックデータ、ログ、エージェントノート、クロールされたコーパスなど）を操作します。これらのワークロードは通常、継続的にアクティブではなくタスク駆動型であり、コンピューティングリソースは97%以上の時間アイドル状態になります。その結果、大規模な常時稼働のベクトルデータベースクラスターを使用することは、コストの観点から正当化するのが難しい場合がよくあります。

        Zilliz On-Demand Searchは、オブジェクトストレージとオンデマンドコンピューティングに対して直接課金します（AWS Lambdaと同様で、価格は主に割り当てられたリソースサイズと実行時間に基づき、ストレージコストは基盤となるS3コストに近くなります）。

        これらの常時稼働でないワークロードの場合、On-Demand SearchとServerlessはどちらも従量課金モデルに従います。ただし、当社の実験が示すように、月間アクティブコンピューティング時間が10時間の10億ベクトルワークロードの場合、On-Demand Searchの総コストはServerlessの約1/15（&#36;318 vs. &#36;4,937）になります。

        詳細については、[オンデマンド検索のクイックスタート](./quick-start-to-on-demand-search)および[オンデマンドコンピューティングコスト](./on-demand-compute-cost)をご参照ください。

        **外部データレイク検索**

        Zilliz Vector Lakebaseは、完全マネージドのストレージとクエリコンピューティングを提供すると同時に、既存のデータレイクインフラストラクチャとガバナンスパイプラインを持つお客様もサポートします。

        AIワークロードにとって、主要な課題は、レイクデータ上で効率的な検索とセマンティック探索を直接可能にすることです。SparkやRayなどの従来のシステムは、インデックスによる高速化されたセマンティック検索ではなく、全データスキャンとマップリデュース計算に最適化されています。

        これに対処するため、Zillizは外部コレクションモードを提供します。これは、顧客所有のレイクテーブルへのゼロコピーの論理マッピングであり、その上に高性能インデックス作成と全スペクトルの検索機能を構築します。

        既存のデータレイクのインデックス作成と高速化方法については、[外部データレイク検索のクイックスタート](./quick-start-to-external-data-lake-search)をご参照ください。

        Vector Lakebaseは、Zilliz Cloudコンソール、REST API、PyMilvus、Zilliz CLIからアクセスできます。これは、コンピューティング、ストレージ、ストレージリクエスト（Query CU、インデックス作成 CU、Project データベース Storage、Storage Requestsを含む）に対して使用量ベースの課金を導入します。

        ## Milvus 3.0 パブリックプレビュー\{#milvus-30-public-preview}

        Vector Lakebaseのローンチに伴い、ZillizはMilvus 3.0のパブリックプレビューもリリースします。このバージョンでは、Milvusはオープンデータ形式と、既存のデータレイクや大規模データ処理エンジンとのより広範な統合を通じて、ベクトルデータベース機能をAIデータインフラストラクチャスタックに拡張します。

        <Admonition type="info" icon="📘" title="Notes">

        このリリースでは、Milvus 3.0の機能はオンデマンドクラスターでのみサポートされます。サービングクラスターはまだサポートされていません。

        </Admonition>

        **外部データおよびストレージ形式**

        - **外部コレクション** — データをMilvusにコピーせずに、オブジェクトストレージ（Parquet、Lance、Vortex、Iceberg）上のデータを直接参照します。Milvusはスキーマ、インデックス、クエリ実行のみを管理します。増分リフレッシュにより、コレクションをソースファイルの変更と同期させ、単一のデータセットを複数のインスタンスから同時に提供できます。

            詳細については、[外部コレクション](./external-collection)をご参照ください。

        - **外部バックフィル** *(プライベートプレビュー)* — ダウンタイムなしで、稼働中のコレクション上の埋め込みモデルをアップグレードします。`AddCollectionField`で新しいベクトルフィールドを追加し、スナップショットで一貫した開始点を固定し、埋め込みジョブをオフラインで実行し、通常の取り込みパスを通じて値を書き戻します。新しい列にインデックスが作成されると、アプリケーションは切り替わります。

            *外部バックフィルのプライベートプレビューに参加するには、[お問い合わせください](https://zilliz.com/contact-sales)。*

        **スキーマとデータモデリング**

        - **Null Vector** — 6つのベクトルタイプすべてでベクトルフィールドをNULL許容にします。検索中にNULL行は自動的にスキップされ、検索品質に影響を与えず、NULLベクトルは実質的にストレージを消費しません。既存のコレクションは、再構築なしでオンラインで`AddCollectionField`を使用して新しいNULL許容ベクトル列を追加できます。

            詳細については、[NULL許容フィールド](./nullable-fields)および[デフォルト値](./default-fields)をご参照ください。

        - **EmbList + DiskANN** — エンティティごとに可変長のベクトルリストを保存し、DiskANNを介してディスク上にインデックスを作成します。長文書、ColBERTのような後期相互作用モデル、マルチモーダルエンティティに適しており、大規模コーパスサイズでもRAMを制御下に保ちます。

            詳細については、[構造体配列](./use-array-of-structs)および[構造体配列演算子](./struct-array-filtering)をご参照ください。

        - **MinHash DIDO（文書入力、文書出力）** — MINHASH_LSHにサーバー側のMinHash関数を追加します。Milvusは挿入、一括挿入、検索時に自動的にシグネチャを計算します。重複排除、フィンガープリンティング、盗用検出ワークフローでアプリケーション側の前処理は不要です。

            詳細については、[MinHash関数](./minhash-function)をご参照ください。

        **検索とランキングの制御**

        - **Query / Search Order By** — 検索およびクエリ結果に対する複数フィールドの順序付けで、フィールドごとにASC/DESCを指定し、カーネルにプッシュダウンされます。複合ランキングのための過剰フェッチやクライアント側での再ソートは不要です。

            詳細については、[基本ベクトル検索](./single-vector-search#sort-search-results-by-scalar-fields-or-private)、[グループ化検索](./grouping-search#order-groups-by-a-scalar-field-or-private)、[クエリ](./get-and-scalar-query#sort-query-results-or-private)をご参照ください。

        **データライフサイクルと運用**

        - **スナップショット** — コレクションのポイントインタイムの読み取り専用ビューで、データをコピーせずに既存のセグメントを参照します。バッチジョブはMVCCスタイルの分離下で実行され、ライブコレクションは書き込みを続けます。A/B評価、重複排除、バックフィル検証に適しています。

            詳細については、[スナップショット](./snapshots)および[スナップショットの管理](./manage-snapshots)をご参照ください。

        - **エンティティTTL（行レベルのTTL）** — `Timestamptz` TTLフィールドによる行ごとの有効期限。期限切れの行は自動的に再利用され、コンプライアンス保持、セッションデータ、会話履歴をカバーします。アプリケーション側でのクリーンアップは不要です。

            詳細については、[コレクションTTLの設定](./set-collection-ttl)をご参照ください。

        - **強制マージ** — オフピーク時間帯に明示的にセグメントのコンパクションをトリガーし（同期または非同期）、クエリレイテンシのジッターやセグメント断片化によるストレージオーバーヘッドを削減します。

        **テキストおよびSparkによるデータ処理**

        - **カスタム辞書とトークナイザー** *(プライベートプレビュー)* — FileResourceメカニズムを介して、カスタムトークナイザー辞書、同義語リスト、ストップワードリスト、分解ルールを登録します。BM25、アナライザー、テキストマッチに反映され、アプリケーションコードに分散されるのではなく、一元的にバージョン管理されます。

        - **Sparkセマンティック重複排除** *(プライベートプレビュー)* — 大規模Sparkデータ処理におけるセマンティック重複排除をサポートします。

        - **Spark異常検出** *(プライベートプレビュー)* — Sparkベースのデータ処理中に異常なレコードやパターンを検出します。

            *上記の機能のいずれかのプライベートプレビューに参加するには、[お問い合わせください](https://zilliz.com/contact-sales)。*

        ## 外部ボリューム\{#external-volumes}

        Zilliz Cloudは、管理ボリュームに加えて外部ボリュームをサポートするようになりました。外部ボリュームは、お客様のクラウドオブジェクトストレージ内のバケットまたはパスへの読み取り専用の参照であり、Zilliz Cloudがインポート、移行、外部コレクションワークフロー用にソースデータをその場で読み取れるようにします。最初にデータをZilliz Cloudにコピーする必要はありません。

        - **データがすでに存在する場所で使用** — 外部ボリュームをAWS S3またはGoogle Cloud Storageパスにポイントします。データはお客様のバケットに残り、Zilliz Cloudは必要なときだけ読み取ります。

        - **制御されたリージョンアクセス** — アクセスはストレージ統合とZilliz Cloud RBACを通じて管理され、許可されたプロジェクトユーザーのみが外部ボリュームを作成または管理できます。

        詳細については、[外部ボリューム](./external-volume)をご参照ください。

        ## 大規模TopK\{#large-topk}

        大規模TopKがコレクションレベルでサポートされるようになり、有効化されたコレクションで返されるエンティティの最大数が16,384から1,000,000に拡張されました。サービングクラスターとオンデマンドコンピューティングの両方で利用可能で、データマイニングやバッチ分析のワークロードに最適です。候補生成、モデル評価、大規模類似性検索などのユースケースで、より広範な候補のリコールを可能にします。

        詳細については、[大規模TopKの使用](./use-large-topk)をご参照ください。

        ## 機能強化\{#enhancements}

        - **リージョン対応プロジェクトガバナンス** — プロジェクトにリージョン制約が追加され、企業がデータの保存場所を管理し、地域データプレーンへのアクセスを明示的に保つのに役立ちます。リージョンモデルは、Zilliz CloudコンソールとAPIの両方に反映されます。

        - **Zilliz CLIの更新** — Zilliz CLIがこのリリースの変更をカバーするように更新されました。Lakebase、外部ボリューム、リージョン対応操作、価格関連の更新が含まれます。詳細については、[Zilliz CLI](https://github.com/zilliztech/zilliz-cli)のエクスペリエンスをご参照ください。
